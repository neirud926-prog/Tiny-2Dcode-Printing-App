# 2D Code Print

Portable Windows app that prints GS1 DataMatrix labels carrying an Internal GTIN, Expiry and Lot, so BCS can scan NLTH Pharmacy packs that have no manufacturer DataMatrix. See [GLOSSARY.md](GLOSSARY.md) and [docs/adr/](docs/adr/).

## Development

A Tauri app (`src-tauri/`, WebView2 from Windows): `src/tauri/` sets the platform to Rust file commands and runs the shared app service (`src/app/service.ts`) in the webview, behind the `window.api` contract (`src/preload/api.ts`). The Rust file commands refuse, with `EACCES`, any path outside `LabelData`, the folders and files chosen in the dialogs this session, and the log files (`print-log-…`/`import-log-…`/`template-log-…`) of a log folder saved earlier. One instance per PC. Requires Node 22.12 or later and Rust.

```sh
npm install           # install dependencies
npm test              # run the tests (vitest)
npm run build         # typecheck and build the webview to out-tauri/ (works on any OS)
npm run tauri:dev     # start the app with hot reload (Windows; needs the WebView2 Runtime)
npm run tauri:build   # typecheck, build the webview, then src-tauri/target/release/tiny-2dcode.exe (no installer)
cd src-tauri && cargo check --target x86_64-pc-windows-msvc   # compile-check the Rust side from any OS
cd src-tauri && cargo test   # the path-scope, error-code and driver-paper tests (on Windows; elsewhere: rustc --edition 2021 --test src/scope.rs, and src/paper.rs)
```

CI (`.github/workflows/ci.yml`) runs the tests on every push and pull request, then builds the Windows `.exe` as `2DCodePrint-<version>.exe` and keeps it as a workflow artifact for 14 days.

### Releasing

1. Set `"version"` in `package.json` (e.g. `0.3.0`) and push to `main`.
2. Push the matching tag: `git tag v0.3.0 && git push origin v0.3.0`, or run the CI workflow by hand on `main` (Actions → CI → Run workflow) with **Publish release** ticked, which creates the tag. CI builds the app and publishes a GitHub Release with `2DCodePrint-<version>.exe` attached and generated notes. A tag that does not match `package.json` fails the release.

To test the release job without publishing anything, run the CI workflow by hand with **Release dry run** ticked: it creates a draft release, checks exactly that one `.exe` is attached, and deletes it.

## Deploying on the shared drive

1. Download `2DCodePrint-<version>.exe` (a few MB) from [Releases](https://github.com/neirud926-prog/Tiny-2Dcode-Printing-App/releases). It is the whole app: no installer, no admin rights. It needs the Microsoft Edge WebView2 Runtime, which Windows 11 and up-to-date Windows 10 already have. For a PC that cannot run WebView2, v0.2.1's `2DCodePrint-0.2.1-portable.exe` (Electron, about 100 MB) stays on Releases; it is no longer updated, and must not share a `LabelData\` with v0.3 or later, whose files may change format ([ADR-0003](docs/adr/0003-tauri-only-from-v0-3.md)).
2. Copy it to a folder on the pharmacy shared drive that every staff member using the app can write to, e.g. `S:\Pharmacy\Label App\`. Every PC runs that same file. To upgrade, close the app on every PC, replace the `.exe` with the new one and keep `LabelData\`. The header shows the running version, e.g. `v0.3.0`.
3. First launch: Setup asks for the Item List import (shared by every PC), then for this PC's printer and label size with a test print. Every other PC asks only for its own printer and test print. Later launches open straight to the label screen. Whenever there is no Stock Onhand dated today, a launch first asks to **Import** today's Stock Onhand report (shared by every PC) or **Skip** (type Lots by hand until the next launch).

- **`LabelData\` is created next to the `.exe`** (see [Data folder](#data-folder)). It holds the shared data and each PC's settings as sealed `.dat` files: do not edit, rename or move them, since a file changed outside the app is refused. Print and import logs are CSV files in `LabelData\logs\` unless the log folder was changed under **Settings**. If the app cannot write there, it says so at startup: move the `.exe` to a folder you can write to.
- **Windows SmartScreen may warn.** The `.exe` is not code-signed, so Windows may show "Windows protected your PC" on first run or when it is downloaded: choose **More info → Run anyway**, or unblock it under the file's **Properties**, or ask IT to allow it.
- **Offline.** The app makes no network calls: no auto-update, no telemetry, no remote content. Updates are manual, from Releases.

## Brother PT-P900W setup (tape)

A tape printer takes the tape from its own driver, not from the app ([ADR-0004](docs/adr/0004-tape-paper-from-driver-preferences.md)), so each PC with a PT-P900W is set up once in Windows and once in the app:

1. **Windows**: Settings → Bluetooth & devices → Printers & scanners → Brother PT-P900W → **Printing preferences** (not Printer properties). Set the tape width to the cassette loaded (e.g. 24 mm) and the length to the Tape Size's length (e.g. 40 mm); set the margin (feed) to its minimum and choose the cut options (auto cut, half cut, chain printing) there. **Apply**.
2. **App, Settings**: under Label Sizes, **Add** a **Tape** size with the same tape width and length (e.g. "24 mm tape × 40 mm"); choose it as **Label in this printer**; set **Printer resolution** to **360 dpi**; choose the printer; **Test print**. The test label shows its outline and the printable band edges: adjust the X/Y offsets until it sits on the tape, then **Save**.

Before every print on a Tape Size the app reads the driver's tape. A different tape width is refused ("The printer is set to 36 mm tape; set 24 mm in its Printing preferences."); a different length prints with a warning; when the driver reports nothing the label prints with a warning to check the tape. GTIN Labels print on 18, 24 or 36 mm tape; Custom Labels on any tape their Template fits (code and text inside the printable band at every Printer resolution). Templates made for a die-cut Label Size do not print on tape: make one for the Tape Size.

## Data folder

The app keeps its data in `LabelData\` next to the `.exe` (in development, `LabelData/` in the project folder, which git ignores) and checks at startup that it can write there. Every PC running the app from the same folder shares it.

- `items.dat`: the Item List, shared by every PC: Item Code, drug name and base unit from the HA file `item_phq.txt` (tab-separated, latin1), with the file's name and date and who imported it where. Imported in the first Setup step, "Item List", and again under **Settings** (**Re-import Item List**) or from the unknown Item Code dialog. A file is refused, and the Item List in use kept, if it is empty, most rows have fewer than 15 columns (the wrong file), or more than 1% of rows are bad (an Item Code that is not 6 characters from the 40 of ADR-0002, or no drug name or base unit); a repeated Item Code keeps its first row. A missing or changed `items.dat` sends the app back to the Setup step "Item List".
- `stock.dat`: the Stock Onhand, shared by every PC: each item's Lots with Expiry (`YYMMDD`), UOM and quantity, from the Oracle report "HA: INV Stock onhand with lot details" (a `.ps` file that is plain text; `.txt` and `.csv` are accepted too; UTF-8 or Windows-1252), with its Report Date, Organization and Subinventory, the file's name and date and who imported it where. Imported from the launch prompt, under **Settings** (**Import Stock Onhand**) or from the label screen when the one in use is not today's; each import replaces it. The report needs a `Report Date:` line in its header block and the columns Item Code, Item Description, Lot Number, Expiry Date, UOM and Onhand Quantity (found by name; Item Code and Lot Number may be Excel text `="…"`; an unquoted comma in a description is recovered in the standard 11-column layout). Rows with the same Item Code and Lot are merged by summing quantity; rows without a Lot are skipped. A file is refused, and the Stock Onhand in use kept, without a Report Date or a required column, with no rows with a Lot, or with more than 1% bad rows (an invalid Item Code, Expiry Date or quantity). Lots can be picked from it only on its Report Date.
- `pending.dat`: the Pending Labels, shared by every PC: label requests (Item Code, Pack Volume if known, Expiry, Lot, copies, who and when) saved from the unknown Item Code dialog (**Save as Pending Label**) because the Item Code is not in the Item List yet. Every change (save, delete, claim for printing, delete expired) is made while holding the lock file `pending.lock`, so two PCs never overwrite each other. A lock older than 30 seconds, left by a PC that stopped mid-change, is taken over; its age is judged by the file server's clock (from a short-lived `pending.lock.clock-<id>` file the app makes in `LabelData` and deletes again, so a PC with a wrong clock cannot break a live lock). A changed `pending.dat` is refused, never replaced. The **Pending Labels** button on the label screen shows the count and lists them; they are checked again after every Item List import (here or on another PC) and whenever the window comes back to the front. Those whose Item Code is now listed show as ready and print with one click through the same checks, self-check and print log as any label. One whose Expiry has passed shows as Expired and cannot print; **Delete expired** removes all of them at once. A Pending Label is removed when it prints (put back if the print fails) or when deleted. A liquid saved without a Pack Volume asks for one before it prints. Up to 200 are kept, expired ones included.
- `templates.dat`: the Templates staff made on the **Custom Label** tab (**New template**, **Copy**, **Edit**, **Rename**, **Delete**), shared by every PC, changed only while holding `templates.lock` like `pending.dat`. Each is for one Label Size, has a name unique ignoring case (Layouts 1 and 2 included, which are built in, never stored, and can only be copied), one code and up to 6 text lines, each fixed or fill-in. A Template is saved only if the code is at least 1 mm (or its quiet zone, whichever is more) from each edge, every text box is at least 1 mm inside the label, and no text box overlaps the code or its quiet zone; the designer moves elements on a 0.5 mm grid. A Label Size used by a Template cannot be deleted. Saving a Template that another PC changed since it was opened is refused ("open it again"), so one PC never silently undoes another's change. A damaged `templates.dat` stops only the stored Templates; Layouts 1 and 2 still print.
- `labelsizes.dat`: the Label Sizes added under **Settings**: die-cut labels (name, width and height in mm) and Tape Sizes (name, tape width 3.5–36 mm and length in mm), shared by every PC and changed only while holding `labelsizes.lock`. The Small Label (34.4 × 25 mm) is built in, always first, never stored. GTIN Labels print on it, or on an 18, 24 or 36 mm Tape Size with the GTIN tape layout (the code at the left, the text to its right; a print is refused, naming the minimum length, when the Tape Size is too short).
- `pcs\<PC name>.dat`: this PC's printer, its Printer resolution (203, 300 or 360 dpi; 203 by default), the Label Size loaded in it (Small Label by default), X/Y offsets for each Label Size, and the log folder; set in the Setup step "Printer" (after the Item List) and changed under **Settings**. A v0.2 file is upgraded when first read: 34.4 × 25 mm becomes the Small Label; any other size is added to `labelsizes.dat` as "W × H mm" and loaded, with its offsets.
- `logs\print-log-YYYY-MM-<PC name>.csv`: one line per print: Date Time (local), Windows User, PC, Item Code, Pack Volume (mL), Internal GTIN, Expiry (YYYY-MM-DD), Lot, Copies, Kind (`GTIN` or `Custom`), Template, Code data, Text (the lines, joined by ` | `). A GTIN Label leaves the last three empty; a Custom Label leaves the GTIN columns empty. Each PC writes only its own file. Test prints are not logged. The log folder can be moved under **Settings**. In the month a PC upgrades from v0.2, its existing file keeps the old 9-column header, so the four new columns have no heading there until the next month's file. A value starting with `=`, `+`, `-` or `@` is written with a leading `'` in every log, so Excel shows it as text, not a formula.
- `logs\import-log-YYYY-MM-<PC name>.csv`: one line per import, accepted or not: Date Time (local), Windows User, PC, Kind (`Item List` or `Stock Onhand`), File (full path), Rows imported, Bad rows, Result (`Imported`, `Refused: <why>`, or `Failed: <why>` when the file could not be read or saved).
- `logs\template-log-YYYY-MM-<PC name>.csv`: one line per Template save, copy, rename or delete, done or refused: Date Time (local), Windows User, PC, Action (`Save`, `Copy`, `Rename`, `Delete`), Template (`old → new` for a rename or copy), Result (`Saved`, `Copied`, `Renamed`, `Deleted` or `Refused: <why>`).

On the label screen, an Item Code must be in the Item List: its drug name shows on screen (never on the label), and a liquid (base unit `ML`) needs a Pack Volume choice, 30 / 60 / 120 / 240 / 480 mL or Other (Pack Volume digit 0). An unknown Item Code cannot be printed; a dialog offers to import a newer Item List or to save the label as a Pending Label. The app checks the Item List again before every print.

The Item Code field also takes a scan (keyboard-wedge scanner, Enter suffix). On Enter or on leaving the field, the Item Code is taken from a plain 6-character code (typed, or an out-patient dispensing-bag label), a shelf label in the shapes BCS reads (NLTH's QR `ITEMCODE_BIN_B<hash>aR` with a 4-character BIN, or another site's plain `ITEMCODE_BIN` with a BIN of 2–6 characters other than `_`, e.g. PMH's `AA 9`), or a 13-character in-patient dispensing-bag label (4 letters or digits, the Item Code, 3 letters or digits; 13 digits is an EAN-13 and is refused). Spaces inside an Item Code are kept; spaces around it are trimmed only when the value fits no pattern as it is. Anything else is refused with "Not an Item Code, shelf label or dispensing-bag label." ([`src/core/scanInput.ts`](src/core/scanInput.ts)).

Once the Item Code is found, the Lot picker lists that item's Lots from today's Stock Onhand, earliest Expiry first, each with its Expiry (`dd MMM yyyy`) and quantity, plus **Type lot manually**. Picking a Lot fills Lot and Expiry exactly as recorded and locks both fields until **Type lot manually** (which clears them). A Lot the Lot rules refuse (e.g. one with a space) or whose Expiry has passed is shown but cannot be picked; a short expiry is warned about as for a typed one. A Stock Onhand dated another day cannot be picked from: the picker shows its date and offers to import today's file. The header shows the Stock Onhand's Report Date and Subinventory, or that it is stale or missing.

`.dat` files are sealed (`TDCP`, a format version byte, HMAC-SHA256, gzipped JSON) and replaced atomically, so a file changed outside the app is refused and other PCs never read a half-written one. Sealing stops casual edits; it is not encryption.

## Internal GTIN test cases

[`test-vectors/internal-gtin-v1.csv`](test-vectors/internal-gtin-v1.csv) lists synthetic Item Code → Internal GTIN pairs for scheme v1 ([ADR-0002](docs/adr/0002-internal-gtin-scheme-v1.md)), so BCS, RxStation and this app can prove their encoders identical. Columns: `item_code` (always quoted, since Item Codes may contain spaces), `pack_volume_digit`, `internal_gtin`. Regenerate it with `npm run test-vectors`.

To also run the codec and the Item List parser over a real Item List locally (never commit it): `ITEM_LIST_PATH=/path/to/item_phq.txt npm test`. The committed `test-fixtures/item_phq-synthetic.txt` is a made-up Item List in the real layout, and `test-fixtures/stock-onhand-synthetic.ps` a made-up Stock Onhand report in the real layout (Windows-1252, CRLF).
